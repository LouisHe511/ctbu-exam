# 架构与取舍

这份文档记录的是**为什么这样做**，而不是代码里能读到的「做了什么」。按问题组织，每个都来自真实踩坑。

---

## 1. 为什么后端不用 Web 框架

`pay_service.py` 基于标准库 `http.server`，手写路由。

**代价**：没有自动参数校验、没有中间件、没有 ORM，路由是一个 300 行的 `if parsed.path == ...` 长链。

**收益**：部署面积极小。一台 2C2G 的机器，`apt install python3-psycopg2 python3-cryptography` 之后，把 `.py` 文件 `scp` 上去、写一个 systemd 单元就能跑。不需要虚拟环境、不需要 gunicorn、不需要担心框架自身的安全通告。

这个项目在很长一段时间里只有一个人维护。**运维复杂度是真实成本**，比框架带来的开发效率更重要。

如果重来一次，在流量增长到需要多进程之前，这个选择仍然成立。

## 2. 支付：为什么不信任前端的「支付成功」

**问题**：用户点完支付跳回来，前端知道「他付了」，但不知道「钱到了」。

早期版本在跳回后直接弹「支付成功」，结果出现过**用户取消支付也弹成功**、以及**付了钱但因为回调延迟没开通**两种相反的假象。前者伤信任，后者更伤信任。

**现在的模型**：三条独立的确认路径，全部以服务端为准。

```
① 平台异步回调  ──→ 验签 → 金额校验 → 幂等开通
② 前端主动查单  ──→ /api/pay/recheck → 按订单渠道问平台
③ 页面轮询      ──→ 每 5 秒查一次，最多 5 分钟
```

三条路最后汇到同一个函数，只有它返回 `paid` 才弹窗。

**关键细节**：查单要**按订单实际走的渠道**去问。支付宝的订单去问易支付，答案永远是「没有这笔」，于是永远等不到开通。这个 bug 在回调丢失时才会暴露，而回调丢失本身很罕见——所以它藏了很久。

**另一个细节**：`alipay.trade.query` 的请求签名里，`sign_type` **必须参与**；而异步通知验签时 `sign_type` **不参与**。两套口径，共用一个拼串函数就会出错。支付宝会把它的待签串原文返回给你，照着对就能看出少了什么。

## 3. 并发下单：为什么把判断放进数据库

前端可以连点两次「确认支付」，也可以在两个标签页同时下单。如果「是否已有待支付订单」的判断写在 Python 里，两个请求会同时读到「没有」，然后都插入。

**做法**：下单、开通、会员叠加全部下沉为 PostgreSQL 函数，用行锁和唯一索引保证互斥。

```sql
-- 伪代码
select ... from payment_orders
 where user_id = uid and status = 'pending'
   for update;              -- 行锁，第二个请求会等
```

好处：无论多少个进程、多少个请求，判断都是原子的。
坏处：业务逻辑不在 Python 里，读代码要跳一层，调试也只能看 SQL 日志。

对一个单机部署的项目，这个取舍是值得的——**正确性比可读性优先**。

## 4. 阅读器：短效签名链接

试卷是逐页渲染的图片。如果图片地址是 `https://site.com/papers/123/p1.jpg`，那么任何人拿到一次链接就能永久访问，也能遍历。

**做法**：图片请求带 HMAC 签名与过期时间。

```
/pages/123/p1.jpg?exp=1730000000&sig=abc...
```

后端校验签名与过期时间，15 分钟后失效。用户重新进入阅读器会拿到新链接。

**这不是防破解**，只是把「批量抓取」的成本从「一次遍历」提高到「持续模拟正常阅读」。真要防到底只能视频流 + 水印，代价太大。诚实地说明这一点，比假装安全更重要。

## 5. 移动端支付：H5 拿不到怎么办

理想路径是手机浏览器直接唤起微信 App（H5 支付）。但**微信的 H5 支付不对个体工商户开放**——这是主体类型限制，材料怎么改都过不了。

于是实际矩阵变成：

| 设备 / 容器 | 微信 | 支付宝 |
|---|---|---|
| 电脑 | Native 扫码 | 电脑网站支付 |
| 微信内 | JSAPI（原地弹面板） | 不可用 |
| 手机浏览器 | Native 扫码 / 长按识别 | 手机网站支付 |

**手机浏览器的微信支付因此是弱体验**：用户得长按自己的屏幕识别二维码。这个缺陷无法用技术绕过，只能靠支付宝的手机网站支付补上（支付宝对个体户开放）。

代码里保留了一个 `WECHAT_H5_OK` 开关，注释写明「只留给将来主体升级为企业」。留着它比删掉它更诚实——它记录了一个产品约束，而不是一个待办。

## 6. 会员规则：优先级必须只有一个来源

会员状态被多个因素影响：试用、付费、管理员授予、邀请奖励、活动延长。如果前端、后端、SQL 各算一遍，同一个用户在不同页面会看到不同的到期日。

**做法**：以 `profiles.membership_expires_at` 为**唯一事实**，所有展示都从它派生。

判断顺序固定为：

1. `expires_at = infinity` → 永久
2. 有付费订单且未过期 → 按实际到期日
3. `is_founder` 且未过期 → 展示试用
4. 其他 → 免费用户

界面文案必须与这个顺序严格对应。曾经出现过「徽标写免费试用 1 个月、卡片写永久免费」的自相矛盾——因为两处各自判断了一遍，条件不同。

## 7. 静态资源：为什么部署不能整体 `--delete`

**事故**：某次部署用 `rsync -a --delete` 替换整个 `dist/`，旧哈希的 JS 文件被删。当时还有用户浏览器里缓存着上一版 `index.html`，它引用的 `assets/index-a1b2.js` 已经 404，懒加载失败，**整页白屏**。

**现在的做法**：

```bash
rsync -a --delete --exclude '/assets/' dist/ /var/www/ctbu/   # 非 assets 整体替换
rsync -a dist/assets/ /var/www/ctbu/assets/                   # assets 只合并
find /var/www/ctbu/assets -type f -mtime +30 -delete          # 30 天前的才清
```

代价是 `assets` 目录会缓慢增长，用定期清理兜住。

## 8. 仓库体积：只放代码和文字

这个仓库曾经把试卷 PDF、听力音频（每份 12 MB 的 `.ts`）、教材电子版、报告截图一起提交，`.git` 涨到 **1.6 GB**。GitHub 超过 1 GB 会直接拒绝推送，报 `pre-receive hook declined`——看起来像权限问题，排查了很久。

**结论**：版本库只放代码和文字。二进制素材放本地磁盘与服务器，需要时另行同步。

`.gitignore` 里对 `*.pdf` / `*.mp3` / `*.ttf` 的排除不是为了洁癖，是为了不让仓库再次变成网盘。

## 已知限制

- 单进程后端，QPS 上限取决于最慢的 SQL 查询
- 试卷内容依赖人工整理，入库流程未完全自动化
- 手机浏览器的微信支付只能扫码（见第 5 节）
- 没有单元测试框架，只有若干 `test_*.py` 冒烟脚本
